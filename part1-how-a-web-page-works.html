HTML: structure & meaning

A page is three languages with three jobs: HTML for structure, CSS for looks, JS for behavior. We start with HTML, which is more than "tags that make boxes".

Tap the right side or swipe left →
HTML · anatomy
project-card.html
<article class="card" id="p-42" data-status="open">
  <h3>Riverside Tower</h3>
  <p>7 open items · due <time datetime="2026-11-01">Nov 1</time></p>
  <img src="tower.jpg" alt="Tower crane at dusk">
  <button type="button">Mark done</button>
</article>

Elements, attributes, nesting

An element is an opening tag, content and a closing tag. Attributes add data. Elements nest into a tree. Some are void and have no content (<img>, <input>).

class is for styling/selection, id must be unique on the page, and data-* holds custom data that JS can read via el.dataset.status.

Semantics

Pick elements for meaning, not looks

Every element has built-in meaning that browsers, screen readers, search engines and tests rely on. Looks come from CSS, so choose by what it is:

  1. <header> <nav> <main> <aside> <footer>: page landmarks (screen-reader users jump between them).
  2. <h1>…<h6>: an outline, in order. Don't skip levels for font size.
  3. <button> does something; <a href> goes somewhere. <ul>/<li> for lists, <table> for tabular data, <label> for every input.
Semantics · why it matters
✗ What AI often writes
<div class="btn" onclick="save()">Save</div>
<!-- not focusable, no Enter/Space, not announced as a button -->
<div onclick="go('/projects')">Projects</div>   <!-- no new tab, no link semantics -->
<input placeholder="Email">                      <!-- placeholder is not a label -->
✓ What good looks like
<button type="button" onClick={save}>Save</button>
<a href="/projects">Projects</a>
<label>Email <input type="email" name="email" autoComplete="email" /></label>

A real <button> gives you a lot for free

"div soup" with click handlers is one of the most common problems in AI-generated UI. It also breaks tests that query by role (getByRole("button")).
Forms

A <button> inside a form defaults to type="submit". In React you usually handle onSubmit and call e.preventDefault() to stop the full-page reload.

Forms do a lot natively

native form
<form action="/search" method="get">
  <label for="q">Search</label>
  <input id="q" name="q" required minlength="2">
  <select name="status"><option>open</option><option>closed</option></select>
  <button>Go</button>        <!-- default type="submit" inside a form! -->
</form>
Gotcha: a "Cancel" button inside a form without type="button" submits the form.

The DOM

The browser parses HTML into a tree of live objects. JS reads and changes that tree; the screen follows.

DOM · what it is
document └─ html ├─ head └─ body └─ article.card#p-42 ├─ h3 ── "Riverside Tower" ├─ p ── "7 open items" └─ button ── "Mark done"

HTML text → a tree of objects

The browser reads the HTML once and builds the Document Object Model: one node per element, text run and attribute. After that, the HTML file doesn't matter: the page is the DOM. Change the DOM and the browser re-renders.

Like an ORM's in-memory object graph: you mutate objects, and the system handles the output (here, pixels instead of SQL).
DOM · reading
querySelector returns null when nothing matches, so document.querySelector(".x").textContent throws if the element isn't there yet (for example, if the script ran before the HTML was parsed).

Finding elements

DOM · writing

Core toolkit: createElement, append, remove, textContent, classList, setAttribute, dataset, hidden.

Changing the tree

DOM · security
✗ What AI often writes
el.innerHTML = `<b>${comment.author}</b>: ${comment.body}`;
// body = '<img src=x onerror="steal(document.cookie)">' → runs!
<div dangerouslySetInnerHTML={{ __html: comment.body }} />  // React's version
✓ What good looks like
el.textContent = comment.body;            // treated as text
<p>{comment.body}</p>                      // React escapes {} for you
// if you truly must render HTML: sanitize it first (e.g. DOMPurify)

innerHTML with user data = XSS

innerHTML, outerHTML, insertAdjacentHTML and dangerouslySetInnerHTML with untrusted data are review blockers.
DOM · attributes vs properties

Attributes are the initial markup; properties are the live state. React sets properties, which is why you write value, checked and className.

Two views of the same element

DOM · performance

Reading geometry (offsetWidth, getBoundingClientRect) right after a write makes the browser compute layout immediately. Batch reads, then writes. Frameworks batch writes for you.

DOM writes are cheap; forced layout is not

✗ What AI often writes
for (const row of rows) {
  row.style.width = container.offsetWidth + 'px';  // read → write → read → write…
}   // each read after a write forces a synchronous layout ("layout thrashing")
✓ What good looks like
const w = container.offsetWidth;                   // read once
for (const row of rows) row.style.width = w + 'px'; // then write

CSS: the cascade & the box model

How the browser decides which rule wins, and how big every box really is.

CSS · rules

A selector picks elements; each declaration sets one property. :hover is a pseudo-class (a state), ::before a pseudo-element (a generated part).

Selector + declarations

selectors
/* selector       { property: value; } */
.card h3          { font-size: 18px; }      /* descendant */
.card > button    { margin-top: 8px; }      /* direct child */
.card.done        { opacity: .6; }          /* both classes */
button:hover, button:focus-visible { outline: 2px solid; }
input[type="email"] { width: 100%; }         /* attribute */
li:nth-child(odd) { background: #f4f5f9; }
The cascade
p { color: gray }0-0-1
.note { color: blue }0-1-0
.card p { color: green }0-1-1
#intro { color: red }1-0-0

When two rules disagree

For each property on each element, the browser collects every matching declaration and picks a winner in this order:

  1. Origin & importance: !important beats normal declarations (avoid it).
  2. Cascade layers (@layer), if used.
  3. Specificity: inline style > #id > .class / [attr] / :pseudo > tag.
  4. Source order: if still tied, the last one wins.
Inheritance
inheritance
body { font-family: system-ui; color: #222; }  /* every descendant inherits */
.card { border: 1px solid #ddd; }              /* children don't get borders */
button { font: inherit; }                      /* form controls don't inherit fonts by default */

Some properties flow down the tree

Text properties (color, font-*, line-height) are inherited by children. Box properties (margin, border, width) are not. Set fonts once on body; that's why it works.

Specificity wars are the usual CSS smell: !important, long chains like .page .main .card .title span, or #id selectors in components. Modern React styles are usually scoped (CSS Modules, utility classes, CSS-in-JS) so this matters less, but you'll still see it in overrides.
Box model
content

Every element is a box

From inside out: content, padding (inside the border, takes background), border, margin (outside, transparent). Tap the values:

Box model · box-sizing
Vertical margins between blocks collapse: 20px below one paragraph and 30px above the next gives 30px, not 50px. It doesn't happen inside flex or grid containers, a common source of "why is this spacing different?".

What does width mean?

box-sizing
.a { width: 200px; padding: 20px; border: 2px solid; }
/* box-sizing: content-box (the default): rendered width = 200 + 40 + 4 = 244px */
/* box-sizing: border-box: rendered width = 200px; content shrinks to 156px */

*, *::before, *::after { box-sizing: border-box; }  /* in nearly every reset */
Display & units

block, inline, and how big is 1rem?

  1. block (div, p, h1): starts on a new line, fills the width.
  2. inline (span, a): flows in text; width/height and vertical margin are ignored.
  3. inline-block, flex, grid, none (removed from layout).

Units: px fixed; rem relative to the root font size (respects user zoom settings); % of the parent; vh/vw of the viewport; fr grid fractions.

Layout: Flexbox & Grid

Two layout systems cover almost everything. Flexbox arranges items along one line; Grid places them in rows and columns.

Flexbox · axes
A
B
C
flex-direction:row; justify-content:flex-start; align-items:stretch

Main axis and cross axis

display:flex on a parent lays out its direct children along the main axis (row by default). justify-content distributes along the main axis; align-items aligns on the cross axis. Tap to cycle:

Flexbox · sizing
Flex items default to min-width: auto, so long text refuses to shrink and overflows. The fix is min-width: 0 on the item. Use gap, not margins, for spacing between items.

flex: grow shrink basis

flex
.toolbar { display: flex; gap: 8px; align-items: center; }
.toolbar .search { flex: 1; }          /* = 1 1 0%: take the leftover space */
.toolbar .logo   { flex: none; }       /* never grow or shrink */
.row             { flex-wrap: wrap; }  /* allow multiple lines */
.title { min-width: 0; overflow: hidden; text-overflow: ellipsis; white-space: nowrap; }

Rows and columns, defined by the parent

Grid · areas & responsiveness

Flex or Grid? Content-sized items in a line (toolbars, button groups, chips) → Flex. Aligned rows and columns (page shells, card grids, forms) → Grid.

Whole-page layout in a few lines

grid areas
.page {
  display: grid;
  grid-template-columns: 240px 1fr;
  grid-template-areas: "nav header" "nav main";
  min-height: 100vh;
}
.page > nav  { grid-area: nav; }
.page > main { grid-area: main; }
@media (max-width: 700px) {                    /* phones: one column */
  .page { grid-template-columns: 1fr; grid-template-areas: "header" "main"; }
  .page > nav { display: none; }
}
Layout · review
✗ What AI often writes
.card { position: absolute; top: 112px; left: 340px; width: 387px; }
.title { margin-left: 13px; margin-top: -3px; }   /* magic numbers */
.item:not(:last-child) { margin-right: 8px; }
✓ What good looks like
.cards { display: grid; grid-template-columns: repeat(auto-fill, minmax(240px, 1fr)); gap: 16px; }
.card  { padding: var(--space-4); }               /* design tokens */
.row   { display: flex; gap: 8px; }

What good CSS looks like vs AI-typical

Flag absolute positioning for normal layout, fixed pixel widths that break on phones, negative-margin hacks, and hard-coded colors/spacing where the codebase has tokens.

Events: bubbling & delegation

Clicks, keys and inputs become event objects that travel through the DOM tree. Knowing the route explains a lot of odd UI bugs.

Events · listeners

The handler gets an event object: type, target, currentTarget, key/mouse info, and methods like preventDefault(). Handlers run on the main thread, one at a time.

addEventListener

Event flow
section
article.card
div.actions

Capture, target, bubble

An event travels in three phases: capture from window down to the target, the target itself, then bubble back up. Listeners run during bubbling by default. Tap the button:

Events · target vs currentTarget
stopPropagation and preventDefault are different things, and AI code often mixes them up. stopPropagation also breaks parents that legitimately listen (analytics, "click outside to close" menus), so ask why it's needed.

Who was clicked vs who is listening

event object
card.addEventListener('click', (e) => {
  e.target;          // the innermost element clicked (maybe the <span> inside the button)
  e.currentTarget;   // the element this listener is attached to: card
});
e.stopPropagation(); // stop the bubble here (parents won't hear it)
e.preventDefault();  // cancel the browser default (link nav, form submit, checkbox toggle)
Delegation

One listener for many children

Because events bubble, you can put one listener on a container and work out which child was hit with e.target.closest(). It works for items added later, too.

React does this for you: it attaches listeners at the root and dispatches to your onClick props.
Events · common types
Listeners added in code must be removed when the UI goes away, or they leak memory and fire on dead UI. In React, that's the cleanup function returned from useEffect.

The events you'll see most

  1. click, pointerdown/up: mouse, touch and pen.
  2. input fires on every change; change on commit (blur, select).
  3. keydown: check e.key === "Enter", not old keyCode.
  4. submit on the form, not the button's click.
  5. focus/blur don't bubble; focusin/focusout do.
  6. scroll, resize: fire very often; throttle them or use observers.

Talking to the server: fetch

How the page gets data after it loads, and the error handling that AI code usually gets wrong.

fetch · basics

fetch returns immediately with a Promise (see Part 2 for how promises and await work). The response headers arrive first; the body is a stream you read with .json(), .text() or .blob().

A request returns a Promise

fetch
const res = await fetch('/api/projects?status=open', {
  headers: { Accept: 'application/json' },
});
res.status;          // 200
res.ok;              // true for 200–299
const data = await res.json();   // body is read separately: another Promise

await fetch('/api/projects', {
  method: 'POST',
  headers: { 'Content-Type': 'application/json' },
  body: JSON.stringify({ name: 'Tower' }),    // you stringify yourself
});
fetch · the big gotcha
✗ What AI often writes
try {
  const res = await fetch(url);
  const data = await res.json();   // 500 → parses the error body as "data"
  setProjects(data);               // or throws a confusing JSON SyntaxError on an HTML error page
} catch { setError('Network error'); }
✓ What good looks like
const res = await fetch(url);
if (!res.ok) throw new HttpError(res.status, await res.text());
const data: unknown = await res.json();
setProjects(ProjectList.parse(data));   // validate the shape (Part 2)

A 404 or 500 does not reject

fetch only rejects on network failure (offline, DNS, CORS blocked). An HTTP error status is a successful fetch of an error response. You must check res.ok.

fetch · try it

Handle every outcome

fetch · in the real world
✓ timeout + cancel
const ctrl = new AbortController();
const t = setTimeout(() => ctrl.abort(), 10_000);       // timeout: fetch has none by default
try { const res = await fetch(url, { signal: ctrl.signal }); … }
finally { clearTimeout(t); }

States, cancellation, credentials, CORS

  1. Model loading / error / success explicitly; render each one.
  2. Cancel stale requests with AbortController (search boxes, fast navigation), or results arrive out of order.
  3. Cookies are sent to the same origin by default; cross-origin needs credentials: "include" and server CORS headers.
  4. CORS errors are enforced by the browser. The fix is on the server (response headers), not in fetch options.

Real apps usually wrap this in a data library (e.g. TanStack Query) that handles caching, retries, deduplication and cancellation.

Bringing it together
state / data→ render() →virtual tree→ diff →minimal DOM updates

Why frameworks exist

With plain DOM code, each data change means finding every element that shows it and updating it by hand: the list, the badge, the counter, the empty state. Forget one and the UI drifts out of sync.

React flips this: you write a function from data → UI, and it works out the DOM changes. Everything in this part still applies underneath: semantic elements, CSS layout, bubbling events and fetch.

Recap

How a web page works

  • HTML = structure and meaning: semantic elements, real buttons and links, labelled inputs.
  • DOM = the live object tree; querySelector can return null; textContent over innerHTML.
  • Cascade: importance → layers → specificity → order. Every element is a box; use border-box.
  • Flex for a line (remember min-width: 0), Grid for rows and columns, gap for spacing.
  • Events capture down and bubble up; delegate with closest(); be wary of stopPropagation.
  • fetch rejects only on network failure: check res.ok, handle all states, cancel stale requests.
