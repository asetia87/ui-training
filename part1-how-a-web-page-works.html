The DOM: the page as objects

The browser doesn't keep your HTML as text. It builds a tree of objects that JS can query and change live.

HTML text → object tree
<article class="card">
  <h3>Riverside Tower</h3>
  <button>Mark done</button>
</article>
↓ parse
article.card ← Element object ├─ h3 │ └─ "Riverside Tower" ← Text node └─ button └─ "Mark done"

Every tag becomes a node object

Each node has properties (className, textContent), a parent and children. The DOM is this tree plus the API for working with it.

Like JSON parsed into a Hash/Map of objects, or an ORM's object graph: you work with objects, not raw text.
Reading · querySelector
const title = document.querySelector('.card h3');
title.textContent   // "Riverside Tower"
document.querySelectorAll('button').length  // 1
article.card ├─ h3 ← matched by '.card h3' │ └─ "Riverside Tower" └─ button

Find nodes with CSS selectors

querySelector returns the first match and querySelectorAll returns all of them. They use the same selector syntax as CSS.

Think Project.where(...) or .find_by, but over the DOM tree.
Changing · textContent & classList
title.textContent = 'Riverside Tower ✓';
card.classList.add('done');
article.card ├─ h3 │ └─ "Riverside Tower" └─ button

Change a node and the screen updates

Set a property and the browser re-renders that part of the page. No reload and no server round trip.

Building · createElement + appendChild
const li = document.createElement('li');
li.textContent = 'RFI #' + n;
list.appendChild(li);

    Create nodes, then attach them

    New elements exist only in memory until you append them into the tree, and then they appear on screen. Tap the button to watch both sides change.

    Selectors · who gets styled

    tag selector: every <h3>

    Selectors are queries

    Tag (h3), class (.st), id (#featured), descendant (.card p) and state (:hover). Tap one to highlight what it matches.

    Cascade & specificity
    h3        { color: green; }  /* 0,0,1 */
.title    { color: blue;  }  /* 0,1,0 */
#featured { color: red;   }  /* 1,0,0 ← wins */

    When rules conflict, the more specific one wins

    Specificity is compared like a version number (id, class, tag), and source order only breaks ties. Inline styles and !important override both.

    Config precedence: framework defaults < config/*.yml < ENV vars < CLI flags.

    Section 4 of 5

    JS in the browser

    Events, network calls, JSON and the event loop: the runtime model that everything else, including React, is built on.

    Events · the browser calls you
    btn.addEventListener('click', (event) => {
  log('clicked ' + event.target.textContent);
});
    // tap a button…

    Register handlers, then react

    You don't poll for clicks. You register a callback and the browser calls it with an event object. Clicks, typing, scrolling and form submits are all events.

    Like registering a route → controller action, or subscribing to a message queue topic.
    fetch · HTTP from the browser
    const res = await fetch('/rest/v1.0/projects'); // example
if (!res.ok) throw new Error(res.status);
const projects = await res.json();

    fetch is your HTTP client

    It returns a Promise, a value that arrives later, and await pauses this function without blocking the page. Note that it only rejects on network failure, so check res.ok for 4xx/5xx responses.

    JSON · the shape of data
    response body (text)
    [{"id":42,"name":"Riverside Tower","open_rfis":7}]
    ↓ res.json() ≈ JSON.parse
    JS objects
    projects[0].name       // "Riverside Tower"
projects.map(p => p.id)  // [42]

    Text on the wire, objects in memory

    Your Rails render json: becomes JS arrays and objects in the browser. JSON has no dates or classes, only strings, numbers, booleans, null, arrays and objects.

    The event loop · one thread
    log('1 start');
setTimeout(() => log('4 timeout'), 0);
Promise.resolve().then(() => log('3 promise'));
log('2 end');
    // guess the order, then run…

    Run to completion, then the queues

    Synchronous code runs first. Then the loop drains microtasks (promise callbacks), then takes the next task (timers, clicks, network). A long task blocks everything, including clicks.

    Not a Puma thread pool: picture one worker taking jobs from a queue, one at a time.

    Section 5 of 5 · Mini-lab

    Build it by hand

    A projects list in plain JS: fetch JSON, then build DOM nodes. It's everything so far in about 15 lines, and it shows why React exists.

    The code
    projects.js (vanilla)
    async function loadProjects() {
  const res = await fetch('/rest/v1.0/projects');
  if (!res.ok) throw new Error(res.status);
  const projects = await res.json();

  const ul = document.querySelector('#projects');
  ul.textContent = '';              // clear old list
  for (const p of projects) {
    const li = document.createElement('li');
    li.textContent = p.name + ' · ' + p.open_rfis + ' RFIs';
    li.addEventListener('click', () => li.classList.toggle('done'));
    ul.appendChild(li);
  }
}
loadProjects();

    fetch → JSON → loop → createElement

    Every part is something you've seen. Using textContent rather than innerHTML also prevents XSS: data is never parsed as HTML.

    Try it · edit & run

    A fake fetch returns sample JSON, so it runs offline. Try adding a project or changing the markup, then tap Run.

    Where this gets painful
    // a new RFI arrives… now update by hand:
li.textContent = 'Riverside · 8 RFIs';   // the list
badge.textContent = total;               // the header badge
sidebarCount.textContent = total;        // the sidebar
if (total === 0) emptyState.hidden = false; // …
// forgot one? → UI out of sync 🐛

    Every change, every place, by hand

    With manual DOM code, you track every spot that shows a piece of data. It gets buggy fast as the app grows. React's answer: describe the UI as a function of the data, and let it do the updates.

    Like hand-written SQL migrations for every change vs. declaring the schema and letting a tool compute the diff.
    Recap

    How a web page works

    • HTML = structure, CSS = looks, JS = behavior.
    • DOM = a live object tree; querySelector, textContent and appendChild read and change it.
    • CSS: selectors pick elements, specificity settles conflicts, every element is a box, Flex for a line, Grid for 2D.
    • JS: events call your handlers, fetch returns Promises (check res.ok), and one thread runs everything.
    • Manual DOM updates don't scale, and that's the problem React solves. Next: React, the "why" and the "how".
