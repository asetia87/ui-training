Who builds the HTML?

Every architecture below is a mix of these two ideas. The key question is always where the HTML is produced and when.

Server-rendered

The Rails way you already know

Request in, controller queries the DB, ERB fills in a template, and finished HTML comes back. The browser just displays it.

It's a pure function on the server: request → HTML string. Nothing runs in the browser except the renderer.

The shell, the code, the data

A client-rendered app loads in three waves: a tiny HTML shell, then the JS/CSS bundles, then the JS fetches JSON and builds the page.

The HTML shell
index.html HTML
<!doctype html>
<html>
<head>
  <link rel="stylesheet" href="/assets/main.81bd02.css">
  <script type="module" src="/assets/main.3f9a1c.js"></script>
</head>
<body>
  <div id="root"></div>  <!-- React fills this -->
</body>
</html>

The HTML is almost empty

The server returns the same static file for every URL. All the real UI lives in the JS bundle, which mounts into #root.

Like a servlet container that serves one index.jsp and a JAR: the HTML is a bootloader, not the content.

Two kinds of requests

Splitting them is the whole point: code is static and cacheable, data is dynamic and private.

Code is your deployed JAR; data is the rows in Postgres. You'd never ship both in one artifact.

The server becomes an API

Your controllers stop rendering views and return JSON. The browser-side app owns all the presentation.

This is a Rails API-only controller or a Spring @RestController. The frontend is just another API client, like the mobile app.

Client routing

Routing in the browser

In a SPA, changing pages doesn't mean asking the server for a page. The router is JavaScript.

Client router
react-router TSX
<Routes>
  <Route path="/projects"     element={<ProjectList />} />
  <Route path="/projects/:id" element={<ProjectDetail />} />
  <Route path="*"             element={<NotFound />} />
</Routes>
compare Ruby
resources :projects, only: [:index, :show]

routes.rb, but in the browser

A client router maps URL → component, the same way routes.rb maps URL → controller action. It reads location.pathname and renders the matching component.

Change the URL without a request

Tap a row: the router calls history.pushState to update the address bar, then renders the new view. The Network tab shows only a JSON request, not a page load.

History API
JS
// router internals, simplified
link.onclick = (e) => {
  e.preventDefault();                  // stop the full page load
  history.pushState({}, '', '/projects/42');
  render(matchRoute(location.pathname));
};
window.onpopstate = () =>            // back / forward
  render(matchRoute(location.pathname));

Back button and deep links

pushState adds a history entry, and popstate fires on back/forward. The page itself never reloads, so JS state survives navigation.

Deep links
Ruby
# config/routes.rb
namespace :api do
  resources :projects
end
# every other path → the SPA shell
get '*path', to: 'spa#index',
  constraints: ->(r) { !r.xhr? && r.format.html? }

The server needs a catch-all

If someone refreshes on /projects/42, the server gets that URL. It must return index.html so the client router can take over, or the user sees a 404.

A front controller pattern: one servlet mapped to /* dispatches everything, here the dispatcher just happens to run in the browser.

    SSR

    Render on the server first

    With SSR, a Node server runs your React components for the request and sends real HTML. The page is visible immediately; JS arrives next and makes it interactive.

    Close to Rails ERB, except the template language is React and the same components also run in the browser later.

    The build step

    From source to shippable files

    Browsers only understand HTML, CSS and plain JavaScript. Everything else, TypeScript, JSX, npm packages, must be compiled first.

    Why build?
    .tsx files.tsnpm packages.scss
    ↓ build (Vite / Webpack)
    main.3f9a1c.jsmain.81bd02.cssindex.html

    Your source is not what ships

    The build turns hundreds of source files and thousands of npm modules into a few optimized files in a dist/ folder that any static host can serve.

    This is mvn package: sources plus dependencies in, one deployable artifact out. dist/ is your target/*.jar.
    npm
    package.json JSON

    npm install      # = bundle install → node_modules/

    package.json is your Gemfile

    npm installs packages into node_modules/. package-lock.json pins exact versions, like Gemfile.lock.

    dependencies vs devDependencies = Maven compile vs test/provided scope. Build tools never ship to the browser.
    Modules

    Imports form a graph

    Each file imports others. Starting from one entry point, the bundler walks this graph and includes only what's reachable.

    Bundlers

    Webpack and Vite

    A bundler combines modules into a few files, drops unused exports (tree shaking), minifies, and splits rarely used screens into lazy chunks. Webpack is the veteran; Vite is the fast modern default.

    Like a shaded/fat JAR built with ProGuard: merge dependencies, strip what's unused, shrink names.
    Transpiling
    you write TSX
    const Row = ({ p }: { p: Project }) =>
  <li className="row">{p.name}</li>;
    ↓ esbuild / Babel / tsc
    browser gets JS
    const Row = ({ p }) =>
  jsx("li", { className: "row", children: p.name });

    TS and JSX become plain JS

    Transpiling strips type annotations and rewrites JSX into function calls. Type checking is often a separate tsc --noEmit step in CI, because the fast transpilers skip it.

    Like javac erasing generics: List<Project> becomes a raw List in bytecode.

    The hash is a fingerprint

    The hash is derived from the file's contents. Change one line and the name changes, so browsers can cache files forever without ever serving stale code.

    Exactly the Rails asset digest (Sprockets/Propshaft). Same trick, different toolchain.
    CDN caching

    Cache code forever, HTML never

    Hashed JS/CSS go on a CDN with a one-year cache. index.html is never cached long, because it's the one file that says which hashes are current.

    index.html is your service-discovery entry: a tiny pointer that must always be fresh, while the artifacts it points at are immutable.

    Dev server

    npm run dev: instant feedback

    The dev server serves modules on demand and uses Hot Module Replacement: save a file and only that component re-runs in the open tab, without a page reload or lost form state.

    Like Rails' code reloading on steroids. A proxy sends /api to your local Rails or Spring server, so there are no CORS headaches.

    Debug the code you wrote

    A source map maps each position in the minified bundle back to your original file and line, so stack traces and breakpoints use your TypeScript, not a(e).

    Like shipping debug symbols, or a ProGuard mapping file that de-obfuscates an Android crash trace.

    Recap

    Architecture on one card

    • Server-rendered (ERB): the server returns finished HTML. Client-rendered: a shell + JS bundle + JSON, and the browser builds the page.
    • Code (hashed JS/CSS, on a CDN, same for everyone) vs data (JSON from your API, per user).
    • Client routing: pushState + popstate; the server needs a catch-all that returns index.html.
    • SSR paints fast; hydration attaches listeners to the server HTML so it becomes interactive.
    • Build: npm + package.json → transpile TS/JSX → bundle with Vite/Webpack → hashed files + source maps → CDN.
