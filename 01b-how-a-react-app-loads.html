How a React app actually loads

A React app loads in stages: an almost empty page, then the code, then the data. Knowing those stages is how you debug "why is this page slow or blank?"

One row per request, one bar per wait

Each row is an HTTP request, and its bar shows when it started and how long it took. We'll build this waterfall row by row (timings are illustrative).

Like a distributed trace (Datadog/Zipkin spans), but for one page load in the browser.
Request 0 · Connect

Find the server, open a secure pipe

DNS turns the name into an IP, then TCP and TLS set up an encrypted connection. This costs tens of milliseconds once, and HTTP/2 then reuses that connection for the requests that follow.

A blank page, for now

The DOM is a handful of nodes and nothing is visible yet. If the JS fails to load, it stays blank. That's the core trade-off of client-side rendering.

Requests 2–4 · The code

The browser fetches the bundles

The parser finds the <link> and <script> tags and fetches all three in parallel over the same connection. Because the scripts use defer, they run in order once the HTML is parsed.

Look at the sizes: the code is ~100× bigger than the HTML. Bundle size is usually the first lever for load time.
What is a bundle?

Hundreds of source files, compiled into a few bundles

At build time, a bundler compiles TypeScript and JSX into plain JS (browsers can't run TS), pulls in libraries, then minifies. Vendor code is often split out because it changes less often.

Like rails assets:precompile or building a fat JAR: many sources become a few deployable artifacts.
Hashed filenames + CDN

The filename is the version

The hash is computed from the file's contents, so bundles can be cached for a year at the CDN and in the browser. A deploy produces new names, and the short-cached HTML shell points to them.

Content-addressed, like a git SHA or a Docker image digest: same bytes, same name.

React takes over #root

Once the bundles run, React renders your component tree and creates real DOM nodes inside the empty div. From now on, React owns everything inside #root.

Skeleton first, data second

React renders immediately with what it has, which is no data yet. A good component shows a skeleton or spinner instead of an empty screen or a crash on undefined.

When reviewing AI code, check that every data-driven component handles loading, error and empty states.

A hook asks your API for data

After the first render, an effect (or a data hook like React Query's useQuery) calls fetch. It's an ordinary HTTP request carrying the user's session cookie or bearer token, exactly what your Rails controllers already authenticate.

Rails answers with JSON only
projects_controller.rb (illustrative)
def index
  render json: current_user.projects
end
response application/json · 4 kB
[{ "id": 42, "name": "Riverside Tower",
   "status": "active" },
 { "id": 43, … }]

No HTML, just data

The API returns JSON and has no idea what the page looks like. Notice that the data request starts late: it can't begin until the JS has downloaded, run and rendered.

Code is static. Data is personal.

Every SPA page load mixes the two. Keeping them apart in your head explains caching, auth and most "why is this slow?" questions.

Code ≈ a deployed artifact (JAR, gem). Data ≈ your API responses. Never put secrets or per-user data in the bundle: anyone can read it.

Data becomes UI in the browser

Structure, behavior, data

The HTML is a launcher, the JS is the whole UI program, and the JSON is this user's data. "View source" on an SPA shows almost nothing for this reason.

Clicking a project · client-side routing
🔒 procore.com/

New URL, no page reload

The router intercepts the click and calls history.pushState, so the URL changes but the page and its JS stay loaded. React swaps components, and the only new request is JSON for project 42.

Where the HTML gets built

With ERB, Rails queries the database and returns HTML with the data already in it. In the SPA, Rails returns JSON and the browser builds the HTML. Same data, different place.

Briefly · SSR (server-side rendering)

SSR: render React on the server first

The server runs your React components and sends real HTML with data, so content shows up quickly. The bundle then hydrates that HTML, attaching React and its event handlers. Before hydration finishes, the page looks ready but clicks don't work yet.

Recap · the full waterfall
  • HTML shell → code → data. The page is blank until JS runs, and the data waits for the code.
  • Code is static and hashed, cached for a year, and the same for everyone. Data is per-user JSON and never shared-cached.
  • React builds the DOM from JSON; navigation is pushState plus a JSON fetch, with no reload.
