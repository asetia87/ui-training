Scope, closures & this

Where a variable lives, when it becomes usable, what functions remember, and how this is decided. Get this right and closures, React hooks and half of the "why is this undefined?" bugs make sense.

Tap the right side or swipe left →
Scope · const, let, var
block vs function scope
if (true) {
  let a = 1;
  var b = 2;
}
console.log(typeof a); // "undefined": a stayed in the block
console.log(b);        // 2: var leaked out of the block

Three ways to declare, one default

const = a binding you won't reassign. let = one you will. var = legacy; avoid it in new code.

const and let are block-scoped: they live inside the nearest { }. var is function-scoped: it leaks out of if and for blocks.

Scope · lookup

How JS finds a variable

  1. Look in the current scope (the block or function you're in).
  2. Not there? Look in the enclosing scope, then the next one out.
  3. Reach the module/global scope and still nothing → ReferenceError.

This chain is fixed by where the code is written (lexical scope), not by who calls it.

Hoisting

Declarations are set up before code runs

Before a scope runs, JS registers every declaration in it. What you get before the line runs depends on the kind:

  1. function f(){}: fully usable from the top of the scope.
  2. var x: exists, value undefined.
  3. let / const / class: exist but unusable until their line runs. That gap is the temporal dead zone (TDZ).
TDZ · why it exists
TDZ is about time, not position
const fmt = (n) => `${prefix}${n}`;
fmt(1);                  // 💥 ReferenceError: prefix is in its TDZ
const prefix = '#';
fmt(2);                  // "#2": fine once the line has run

The TDZ is a feature

With var, reading too early silently gives undefined and the bug travels. The TDZ turns that into an immediate, loud error.

A function may mention a later const. It only fails if it is called before that line runs. Watch module-level helpers that run during import.
Scope · gotcha

The classic var in a loop

var i is one variable shared by every iteration. let i gets a fresh binding per iteration, so each callback sees its own value.

Closures · definition

A function remembers the scope it was created in

When you create a function inside another, the inner one keeps a live link to the outer variables, even after the outer function has returned. That bundle (function + remembered variables) is a closure.

Closures capture variables, not values

A closure sees the variable's current value when it runs. In React this shows up as the stale closure: a callback created during an old render keeps reading that render's values.

this · the rule

this is decided at call time

For a regular function, this is set by how it is called, not where it is written:

  1. obj.method() → this is obj.
  2. fn() on its own → undefined in strict mode (modules and classes are strict).
  3. new Fn() → the new object. fn.call(x) / fn.bind(x) → x.
Arrow functions
why arrows became the default for callbacks
class Uploader {
  files = [];
  start() {
    button.addEventListener('click', function () {
      this.files.push(1);    // ✗ this = the button element
    });
    button.addEventListener('click', () => {
      this.files.push(1);    // ✓ this = the Uploader
    });
  }
}

Arrows don't have their own this

An arrow function uses the this of the scope it was written in (lexical this), just like any other variable. It also has no arguments and can't be used with new.

Don't use an arrow as an object method that needs this: { name: "A", get: () => this.name } reads the outer this, not the object.

Objects, arrays & references

Values vs references, copying, immutability and the array methods you'll read in every component.

Reference vs value

Primitives are copied, objects are shared

Primitives (string, number, boolean, null, undefined, bigint, symbol) are copied on assignment. Objects and arrays are stored by reference: assigning copies the pointer, not the data.

Same as Java object references, or Ruby objects: b = a never clones.
Copying

Spread makes a shallow copy

{ ...obj } and [...arr] create a new top-level container, but nested objects are still shared. structuredClone(x) makes a deep copy.

Destructuring
Destructuring a missing nested object throws: const { owner: { email } } = {} → TypeError. Use defaults or optional chaining when data may be absent.

Why React wants new objects

React decides whether something changed with Object.is(old, new), a reference check. Mutate in place and the reference stays the same, so React may skip the re-render.

Modules

Every file is its own scope; only exports leave it. Modules run once, on first import, and are strict mode by default. Bundlers follow these imports to build the app.

import / export

ES modules
// api.ts
export async function getProjects() { … }   // named export
export const PAGE_SIZE = 50;
export default function ProjectList() { … } // one default per file

// page.tsx
import ProjectList, { getProjects, PAGE_SIZE as size } from './api';
import type { Project } from './types';        // type-only: erased at build
Imports are live, read-only bindings: you can't reassign an imported variable. Circular imports can hit the TDZ (a value used before its module finished running). Prefer named exports: they rename-refactor and auto-import better.

The event loop

JS runs on one thread. Here is exactly how it juggles timers, network responses, promises and clicks without blocking.

Event loop · the parts

Four moving pieces

  1. Call stack: the function running right now and its callers. Only one thing runs at a time.
  2. Web APIs (the browser/Node): timers, network, DOM events. They work outside your thread.
  3. Task queue (macrotasks): timer callbacks, events, message handlers, waiting to run.
  4. Microtask queue: promise callbacks (.then, code after await), queueMicrotask.

The loop: run one task until the stack is empty → run all microtasks → maybe render → take the next task.

Event loop · blocking

A long task freezes everything

While your code is on the stack, the browser can't render, scroll handlers can't run, and clicks just queue up. Heavy loops, big JSON.parse calls or huge synchronous renders cause jank.

Microtasks can starve rendering too: a promise chain that keeps queueing microtasks never lets the browser paint. Split big work up, move it to a Web Worker, or yield with setTimeout.
Callbacks
✗ What AI often writes
getUser(id, (err, user) => {
  if (err) return done(err);
  getProjects(user, (err, projects) => {
    if (err) return done(err);
    getRfis(projects[0], (err, rfis) => {
      if (err) return done(err);   // forget one of these and errors vanish
      done(null, rfis);
    });

Before promises: callbacks

A callback is a function you pass in to be called later. Node-style callbacks take (err, result). Nesting several async steps produces the "pyramid of doom", and errors must be checked by hand at every level.

You still use callbacks constantly for events (onClick) and array methods. For one-off async results, promises replaced them.

Promises & async/await

A Promise is an object representing a value that isn't ready yet. Learn them properly and async/await, the syntax on top, becomes obvious.

Promises · what they are
pending→fulfilled(value)
↘rejected(error)
state: pending · handlers registered with .then wait

An object for a future result

A Promise is a placeholder you get back immediately from an async operation. Later, it settles exactly once:

  1. pending: still working.
  2. fulfilled with a value, or rejected with a reason (usually an Error).
  3. Once settled it never changes; late .then calls still get the value.
Promises · creating one

You rarely write new Promise yourself: fetch and most libraries already return promises. It's mainly for wrapping old callback APIs.

Wrapping a callback API

Promises · chaining

Each .then returns a new promise

  1. Return a plain value from .then → the next promise fulfils with it.
  2. Return a promise → the chain waits for it (that's how you sequence async steps).
  3. Throw (or return a rejected promise) → the next promise rejects and skips to the next .catch.
Promises · error propagation
✗ What AI often writes
fetchUser()
  .then(user => {
    fetchProjects(user);        // ✗ not returned: chain doesn't wait,
  })                            //   and its rejection is unhandled
  .then(projects => render(projects))  // projects is undefined
  .catch(show);
✓ What good looks like
fetchUser()
  .then(user => fetchProjects(user))   // ✓ returned: chain waits, errors flow
  .then(projects => render(projects))
  .catch(show);                        // one catch for every step above

Errors flow down to the nearest .catch

The #1 promise bug: a .then callback that starts async work and forgets to return it. In review, check every .then with braces has a return.
Promise combinators
  1. Promise.all: all succeed → array of values; first rejection rejects everything (the others keep running, results ignored).
  2. Promise.allSettled: waits for all, gives {status, value|reason} each. Use for "show what loaded".
  3. Promise.race: first to settle (often a timeout). Promise.any: first to succeed.

async/await · the rules
async function
async function loadProject(id: string) {
  const res = await fetch(`/api/projects/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return res.json();            // Promise<unknown>
}

Four rules cover it

  1. An async function always returns a Promise. return 5 → Promise<5>; throw → a rejected promise.
  2. await p pauses this function only until p settles, then gives the value or throws the error.
  3. The rest of the function after await runs later, as a microtask. The thread is free in the meantime.
  4. Use try / catch / finally for errors, just like synchronous code.

Equality, coercion & missing values

JS converts types silently in some places. Know where, and handle null/undefined on purpose.

Equality

== applies coercion rules; === compares type and value. The one idiom some teams allow is x == null, which matches both null and undefined.

Use ===, almost always

Truthy & falsy
✗ What AI often writes
{count && <Badge n={count} />}   // count = 0 → renders "0"
const pageSize = opts.size || 20; // size = 0 → silently 20
✓ What good looks like
{count > 0 && <Badge n={count} />}
const pageSize = opts.size ?? 20; // only null/undefined fall back

Only eight values are falsy

Falsy: false, 0, -0, 0n, "", null, undefined, NaN. Everything else is truthy, including [], {} and "0".

a || b returns the first truthy operand; a && b returns the first falsy one (or the last). They return values, not booleans.

Different from Ruby, where only nil and false are falsy and 0 is truthy.
Coercion
Everything from <input>, query strings and localStorage is a string. Convert explicitly with Number() and check Number.isNaN.

Where JS converts types for you

Optional chaining & nullish
Don't sprinkle ?. everywhere "to be safe". If a value should always exist, a crash points to the real bug; ?. hides it and renders empty UI. Ask: can this actually be missing?

TypeScript

JS plus a compile-time checker. It feels like Java at first, but works differently in important ways. Then: React props/events, escape hatches, strict mode, and types disappearing at runtime.

Structural typing
structural
interface Point { x: number; y: number }
function len(p: Point) { return Math.hypot(p.x, p.y); }

const v = { x: 3, y: 4, label: 'v' };
len(v);                          // ✓ has x and y: extra props are fine
len({ x: 3, y: 4, label: 'v' }); // ✗ object literal: "excess property" check
class Vec { constructor(public x: number, public y: number) {} }
len(new Vec(1, 2));              // ✓ never declared it implements Point

Shape matters, not names

TS checks whether a value has the right shape. Two types with the same properties are compatible even if they never mention each other. No implements needed.

Unlike Java's nominal types, where a class must declare implements. It's closer to Ruby duck typing, but checked at compile time.
Inference

Two "I don't know" types, opposite meanings

any turns the checker off: everything is allowed and it spreads into everything it touches. unknown means "could be anything, so prove it before use".

catch (e) is unknown in strict mode. Use e instanceof Error ? e.message : String(e), not e.message.

as is a promise to the compiler, not a check

x as Project doesn't convert or verify anything. It tells TS "trust me", so the error moves to runtime. as unknown as T and the non-null ! are louder versions of the same thing.

Every as, !, any and // @ts-ignore in a diff deserves a "why?". AI tools reach for them to silence errors.
Strict mode

Without strictNullChecks, null fits into every type, and most of TS's value disappears. noImplicitAny stops untyped params quietly becoming any. If a PR loosens tsconfig to make errors go away, push back.

Turn on strict, and keep it on

tsconfig
// tsconfig.json
{
  "compilerOptions": {
    "strict": true,                 // strictNullChecks, noImplicitAny, …
    "noUncheckedIndexedAccess": true, // arr[i] is T | undefined
    "noImplicitOverride": true
  }
}

At runtime, there are no types

TS compiles to plain JS and deletes every type. Nothing checks that the server actually sent a Project. Your annotation on res.json() is a guess.

✓ validate at the boundary
import { z } from 'zod';
const Project = z.object({ id: z.string(), name: z.string(), budget: z.number().nullable() });
type Project = z.infer<typeof Project>;          // one source of truth

async function getProject(id: string): Promise<Project> {
  const res = await fetch(`/api/projects/${id}`);
  if (!res.ok) throw new Error(`HTTP ${res.status}`);
  return Project.parse(await res.json());        // throws on a bad shape
}

TS smells in AI-written code

  • any in props, state or API results → ask for real types or unknown.
  • as / ! / @ts-ignore to silence errors → find the real fix.
  • Boolean-flag soup for states → a discriminated union.
  • Copy-pasted interfaces → Pick / Omit / Partial.
  • Generic getJson<T> with no validation → same as as T.
  • useState([]) with no type → never[].

Recap

JS & TS, the whole picture

  • Scope is lexical; const/let are block-scoped with a TDZ; avoid var.
  • Closures capture variables (watch stale closures); this is set at call time, arrows inherit it.
  • Objects are references: spread copies shallowly; never mutate React state; know which array methods mutate.
  • Event loop: sync code → all microtasks → next task. Long tasks freeze the page.
  • Promises chain and propagate errors (return them!); all / allSettled / race / any.
  • async/await: always returns a promise; parallelise independent work; never forget await.
  • ===, falsy 0, ?? over ||, and ?. only when absence is real.
  • TS: structural types, narrowing, discriminated unions, generics, utility types; strict on; unknown over any; validate JSON because types are erased.
