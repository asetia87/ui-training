How the browser turns code into pixels

You know everything up to the moment your Rails app sends the response. This lesson covers what happens after that.

Tap the right side or swipe left to start →
Step 0 · Network

It starts with your response body

The browser sends a GET, and the server streams back text/html. The browser starts parsing the first chunk before the rest arrives, and requests CSS, JS and images as it finds them.

Step 1 · HTML → DOM

Tags become a tree of objects: the DOM

Each tag becomes a node object with a parent, children and properties. JS reads and changes this live tree through the DOM API.

Think of an in-memory object graph, like a loaded ActiveRecord association tree, with a query API for finding nodes.
Step 2 · CSS → CSSOM

CSS becomes the CSSOM, and conflicts cascade

Stylesheets are parsed into the CSSOM. When rules clash, the winner is decided by origin and importance, then specificity, then source order. CSS blocks rendering: nothing paints until it has loaded.

Step 3 · Render tree

DOM + CSSOM = render tree

The browser matches styles to nodes and keeps only what will be drawn, each with its computed style. display:none nodes are left out. visibility:hidden ones stay and still take up space.

Layout: where does every box go, and how big is it?

Layout turns the render tree into exact geometry: x, y, width and height for every box. Boxes depend on each other, so one width change can ripple through siblings, children and parents.

Step 5 · Paint

Paint: boxes become draw commands

Paint records an ordered list of drawing operations: backgrounds, shadows, borders, text. These are rasterized into pixels, often into separate layers.

Composite: stack layers into the frame

The compositor, which runs off the main thread and mostly on the GPU, stacks painted layers into the final image. Moving a layer with transform or fading it with opacity can skip layout and paint entirely.

Where JS fits

JS can change the DOM at any moment

Scripts read and change the tree (el.textContent = "Saved"), and every change can re-trigger style, layout and paint. A plain <script> pauses parsing while it downloads and runs, so apps use defer or type="module".

Not all changes cost the same

Geometry changes force layout and paint for every affected box. Color skips layout, and transform/opacity can skip both.

Reading el.offsetHeight right after a style write forces a synchronous layout. Doing that in a loop is the N+1 query of the frontend, so batch your reads, then your writes.

The event loop

One thread, one loop

JS, style, layout and paint share one main thread. Each turn of the loop runs one task to completion, then drains promise callbacks (microtasks), then may render a frame.

Not like Puma with a thread pool. Picture a single worker taking every request in turn: one slow handler blocks everyone behind it.

Describe what, not how

Hand-written DOM code spells out how: find the node, patch the text, and don't forget the badge. React is declarative: UI = f(state). You change the state and React works out the DOM updates.

The virtual DOM idea

Diff in JS, touch the DOM minimally

React re-runs your components to build a lightweight JS description of the UI, diffs it against the previous one, then commits only the real DOM changes. The point isn't magic speed: you get declarative code with batched, minimal DOM writes.

Recap

The pipeline on one card

bytes→ DOM+ CSSOM→ render tree→ layout→ paint→ composite
  • JS changes the DOM, and each change can re-run style → layout → paint.
  • Geometry changes are expensive; transform and opacity are cheap. Batch reads before writes.
  • One main thread: long tasks freeze input and frames.
  • React: UI = f(state). It diffs, then applies minimal DOM updates.
